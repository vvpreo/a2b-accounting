# План: Слипы транзакций (хранилище документов, локальное распознавание, привязка memo)

## Goal

Банковское приложение на телефоне сохраняет слип (картинку-квитанцию) по каждой операции; в слипе пользователь пишет заметку (memo/note) — к чему относится трата. Слип нужен **ровно для одного**: найти по нему транзакцию и взять заметку, чтобы правильно описать и категоризировать трату. Получатель, канал и прочее уже есть в выписке — со слипа их не берём.

Отсюда две задачи:
1. **Матч** — определить банк, счёт, дату-время и сумму слипа и найти соответствующую транзакцию.
2. **Заметка** — извлечь memo (английский, русский, гипотетически тайский).

## Context

- Приложение работает на localhost Мака; с телефоном связи нет. Слипы выгружаются с телефона в Google Диск, пользователь скачивает их оттуда ZIP-архивом.
- **Только локальная обработка.** Слипы никуда в облако не отправляются. Любая отправка данных в облако обсуждается отдельно; текущий облачный ИИ-агент ([server/src/ai.rs](../../server/src/ai.rs)) — эксперимент и не образец.
- Почтовый ящик как источник не используем.

## Что показал реальный архив (2622 слипа, февраль 2025 — октябрь 2026)

Анализ на стенде (Tesseract + zbar в одноразовом контейнере, данные не коммитятся):

**Состав.** Архив из Google Диска: `vvpreo/KSK/` — 2367 слипов K PLUS (Kasikorn, три счёта: маски `x6813`, `x1337`, `x1802`), `vvpreo/BBK/` — 255 слипов Bangkok Bank (счёт `953-7-xxx734`).
- Слипы BBL — **PNG с расширением `.jpeg`** (скриншоты 1080×2180, имя `BBl-Screenshot-<epoch-ms>`). Тип определяем по сигнатуре, не по расширению.
- В архиве попадаются **не-слипы**: например, QR «переведите мне» (`004999…_20250823_….jpeg`). Нужен статус «не слип».
- Вёрстка K PLUS **меняется**: бирюзовый фон с текстурой (2025), праздничный фон с сердечками (14 фев), серый (2026); в старой вёрстке Transaction ID стоит над Amount, в новой — под ним. BBL — совсем другая вёрстка, поле называется `Note`.

**QR-код** (стандарт Банка Таиланда «Slip Verify», одинаковый для всех банков) содержит только: тип `000001`, код банка-отправителя (`004` Kasikorn, `002` BBL), номер операции, страну `TH`, CRC. Суммы, даты, memo в нём нет. Прочитан у 2366/2367 K PLUS и 242/255 BBL (у переводов внутри BBL QR нет вовсе).

**Номер операции кодирует время** — независимо от OCR и вёрстки:
- K PLUS: `0 1 Y DDD HHMMSS <канал> <номер>` → `016300115855CPM09866` = 2026, 300-й день (27 окт), 11:58:55. Год — одна цифра (десятилетие берём из даты на слипе / даты загрузки).
- BBL `Transaction reference`: `YYYYMMDDHHMMSS…` → `20250716153930…` = 16.07.2025 15:39:30.

**Распознавание (Tesseract, оттенки серого + увеличение ×1.5):**

| | K PLUS (2367) | BBL (255) |
|---|---|---|
| Дата-время (из номера операции или текста) | 2365 | 254 |
| Сумма найдена в тексте | 2364 | 255 |
| Memo/Note извлечена | 2269 | 244 |

Частые ошибки OCR: кириллица вместо латиницы (`ххх-х-х6813-х`, `РМ` вместо `PM`), `O` вместо `0` в номерах, жирная крупная сумма на текстурном фоне иногда не читается. Жёсткая бинаризация портит memo — не используем.

**Матч с выпиской** Kasikorn `x8136` (= маска `x6813`, май—октябрь 2026, 675 операций):
- 542 слипа этого счёта в периоде → **477 привязаны однозначно** (время ±2 мин + точная сумма), **0 неоднозначных**, ни одна транзакция не получила два слипа.
- 65 не привязались: у 62 OCR не прочитал крупную сумму, но в ту же минуту на счёте ровно одна транзакция → привязываются «по времени» с пометкой на проверку.
- Покрытие: у 314 из 332 списаний K PLUS есть слип.

**Пробел:** в июле 2026 всего 17 слипов при обычных 110–170 в месяц — ровно то, что должен ловить учёт загрузок (см. ниже).

**Скорость** (1 ядро): полный OCR тремя языками с увеличением — 1.5 с/слип; только английский по всей странице — 0.8 с; полоса memo тремя языками — 0.3 с. Весь архив — несколько минут в фоне на всех ядрах; обычная пачка — секунды.

## Decisions

- **Отдельное хранилище документов** (`attachments`), общее для любых вложений; у документа свой жизненный цикл (может прийти раньше выписки, остаться непривязанным, быть перепривязанным; при удалении пакета импорта отвязывается, а не удаляется). Файлы — на диске `$FINANCES_DATA_DIR/attachments/<sha256>.<ext>`, метаданные — в SQLite.
- **Источник — загрузка через интерфейс:** файлы по одному, пачкой и **ZIP-архивом** (распаковка на сервере, рекурсивно, только картинки по сигнатуре). Google Drive API — отложено (если вернёмся — сервисный аккаунт).
- **Учёт загрузок:** каждая загрузка — запись в `attachment_uploads` (когда, что загружено, сколько добавлено/дублей/пропущено); документ помнит загрузку, которая его принесла. Это даёт «последняя загрузка N дней назад», историю загрузок и поиск пробелов.
- **Дедупликация** по SHA-256 содержимого и дополнительно по (банк, номер операции) из QR — один и тот же слип, пересохранённый заново, тоже ловится.
- **Распознавание — локально**, Tesseract внутри Docker-образа. Никаких облачных сервисов проверки слипов.
- **С слипа берём только:** банк, счёт (маска), дату-время, сумму — для матча; memo — для описания. Получателя и прочее — из выписки.
- **Не привязываемся к формату конкретного банка или страны.** Распознавание — набор **независимых извлекателей**, каждый отвечает за одно поле и сам по себе ничего не знает о вёрстке:
  1. **Банк** — из QR (тайский Slip Verify — лишь один из декодеров), из названия банка в тексте, из совпадения счёта.
  2. **Счёт** — последовательности цифр с масками (`xxx-x-x6813-x`, `953-7-xxx734`, `****1234`) сравниваются с номерами **счетов пользователя в БД**: совпадение хвоста цифр однозначно даёт и счёт, и банк. Это самый универсальный признак — работает для любого банка.
  3. **Дата и время** — общий разборщик дат по всему тексту (разные порядки, месяцы словами на en/ru/th, буддийский год, 12/24 ч); номера операций, в которые банк зашил время (K PLUS, BBL), — необязательные **подсказки**, повышающие точность.
  4. **Сумма и направление** — все денежные токены текста; приоритет у токена рядом с меткой суммы (`Amount`/`Сумма`/`จำนวน`/`Total`) и у **самого крупного шрифта** (высота слова из OCR). Направление — по словам (`Payment`, `Transfer`, `Received`, `Пополнение`…) и по тому, стоит ли счёт пользователя в роли отправителя или получателя; окончательно подтверждается матчем с транзакцией (debit/credit).
  5. **Заметка** — текст после метки (`Memo`, `Note`, `Remark`, `Заметка`, `Комментарий`, `บันทึกช่วยจำ`…), до следующей метки или конца блока.
  Каждый извлекатель возвращает значение + **источник** (`qr`, `filename`, `ocr`, `ref`) + уверенность; любое поле может остаться пустым. Знания о конкретных банках — только **подсказки**, а не обязательные шаблоны.
- **Слип незнакомого банка** проходит те же извлекатели. Что нашлось — используется; если для матча не хватает данных — документ попадает в «на проверку», где пользователь привязывает его вручную. Новый банк не требует нового кода, а при желании добавляется подсказка.
- **Выписка как проверка.** Транзакции из выписок — независимый источник истины: неточный OCR даёт «не найдено», а не неверную привязку.
- **Скорость** не критична (2–5 с на документ приемлемо): первичная загрузка архива — разовая, в фоне. Оптимизации (английский OCR по странице + многоязычный только по полосе заметки) — по необходимости.
- **Нормализация OCR:** кириллические двойники → латиница в масках/AM-PM, `O`→`0` в номерах.
- **Автопривязка (решение пользователя, 2026-10-27):** документ привязывается автоматически, когда совпадают **время, сумма и направление** и других транзакций, подходящих под это условие, **нет**. Счёт и банк для автопривязки не требуются — это снимает проблему их распознавания (если счёт распознан, он лишь сужает выбор). Неоднозначные и неполные случаи — ручная привязка.
- **Ручная привязка — без распознавания.** В карточке транзакции (перед блоком ИИ-агента) показывается привязанный документ; кнопка «Привязать документ» выводит документы, чьё время попадает в окно вокруг транзакции (±5 мин по умолчанию, ±30 мин, ±1 день), ближайшие сверху, с превью — пользователь выбирает глазами. Время документа на этом этапе берётся из **имени файла** (первый, самый дешёвый извлекатель): номер операции K PLUS, `YYYYMMDD_HHMMSS`, epoch-мс скриншотов BBL. Зональное время слипа (без пояса) читается в часовом поясе пакета импорта транзакции.
- **Колонка 📎** на экране транзакций (сразу после «Баланса», перед колонками 🔗 и Δ): есть ли привязанный документ, клик открывает его. По аналогии с 🔗: пустая ячейка при наведении подсвечивается зелёным, клик сразу открывает подбор документа для этой транзакции; после привязки окно закрывается.
- **Одна колонка «Заметка»** (решение пользователя 2026-10-27) вместо 📎, ИИ и «Комментария»: слева значок — стикер, если пользователь написал комментарий (он ценнее распознанной заметки и перебивает скрепку), иначе скрепка, если привязан документ; справа текст — комментарий, иначе заметка из слипа. Клик в любое место ячейки открывает окно «Документ и комментарий» (превью слипа, данные транзакции, комментарий, подбор документа); в самой ячейке ничего не редактируется. Кнопка ✨ из таблицы убрана — логика работы с категориями будет пересмотрена отдельно. Комментарий уже входит в данные, которые видит ИИ-агент.
- **Удаление при наличии связи.** Удаление транзакции (в т.ч. каскадом — пакета импорта или счёта) документ не удаляет: он становится непривязанным (`transaction_id → NULL`, триггер сбрасывает `match_status` в `unmatched`, миграция 018). Удаление документа транзакцию не трогает — связь хранится только на стороне документа и исчезает вместе с ним. Заметка, уже перенесённая в комментарий транзакции (этап 3б), остаётся в комментарии.

## Data Model

```sql
attachment_uploads (
  id            INTEGER PRIMARY KEY,
  uploaded_at   TEXT NOT NULL,          -- UTC
  source_name   TEXT,                   -- имя ZIP или «N files»
  files_total   INTEGER NOT NULL,
  added         INTEGER NOT NULL,
  duplicates    INTEGER NOT NULL,
  skipped       INTEGER NOT NULL        -- не картинки / не слипы
)

attachments (
  id              INTEGER PRIMARY KEY,
  upload_id       INTEGER NOT NULL REFERENCES attachment_uploads(id),
  sha256          TEXT NOT NULL UNIQUE,
  original_name   TEXT NOT NULL,        -- для архива — путь внутри архива
  mime_type       TEXT NOT NULL,        -- по сигнатуре
  size_bytes      INTEGER NOT NULL,
  kind            TEXT NOT NULL DEFAULT 'slip',     -- slip | not_slip | other
  bank_code       TEXT,                 -- из QR: '004', '002', …
  bank_ref        TEXT,                 -- номер операции
  occurred_at     TEXT,                 -- местное время слипа
  account_mask    TEXT,
  amount_minor    INTEGER,
  memo            TEXT,
  ocr_text        TEXT,                 -- сырой текст для разбора ошибок
  extract_status  TEXT NOT NULL DEFAULT 'pending',  -- pending | done | partial | failed
  transaction_id  INTEGER REFERENCES transactions(id) ON DELETE SET NULL,
  match_status    TEXT NOT NULL DEFAULT 'unmatched', -- auto | probable | manual | ambiguous | unmatched
  UNIQUE (bank_code, bank_ref)
)
```

## Steps

### Этап 1 — Хранилище и загрузка ✅ (сделано 2026-10-27)

Итог: миграция `017_add_attachments.sql` (`attachment_uploads`, `attachments`; статусы — свободный TEXT, без CHECK, чтобы конвейер мог расти), модуль [server/src/attachments.rs](../../server/src/attachments.rs), маршруты `POST /api/attachments/upload/{upload_id}?name=` (сырое тело, ZIP распаковывается на сервере в blocking-потоке) и `GET /api/attachments/{id}/file`, RPC `begin_attachment_upload` / `list_attachment_uploads` / `list_attachments` / `delete_attachment`. Бэкап включает `attachments/` (Stored, без пережатия), restore сливает файлы по строгим именам `<sha256>.<ext>`. Вкладка «Документы» рядом с «Категориями»: загрузка (кнопка и drag & drop на страницу, прогресс через XHR), отчёт о загрузке, история загрузок, «последняя загрузка», фильтры, список, сгруппированный по загрузкам, карточка документа (картинка/PDF + панель результата распознавания с полями и источниками + сведения о файле, удаление с подтверждением).
Проверено на реальном архиве: 2622 файла (454 МБ) загружаются за ~4 с, повторная загрузка — 2622 дубля; PNG-слипы BBL с расширением `.jpeg` распознаются как PNG.
Отклонения от плана: ZIP бэкапа по-прежнему собирается в памяти (с документами это сотни мегабайт RAM на время скачивания) — перевод на потоковую отдачу оставлен на потом.

Исходный план этапа:
- Миграция + `server/src/attachments.rs`: сохранение по хешу, распаковка ZIP (лимиты числа записей и объёма, игнор `..`, `__MACOSX/`, сайдкаров), тип по сигнатуре, запись `attachment_uploads`.
- HTTP: `POST /api/attachments/upload` (multipart) → отчёт `{added, duplicates, skipped}`; `GET /api/attachments/<id>/file`.
- Бэкап/restore включает `attachments/` (ZIP бэкапа сейчас собирается в памяти — перевести на временный файл).
- UI: раздел «Документы» — зона загрузки, список с превью и фильтрами (все / непривязанные / на проверку / не слипы), история загрузок с датой последней.

### Этап 2 — Распознавание (локально)
- Docker-образ: `tesseract-ocr` + `eng`, `rus`, `tha`. QR — Rust-крейт (`rqrr`) без внешних бинарей; подготовка картинки (серый, увеличение, вырезание полосы) — крейт `image`. Tesseract вызывается подпроцессом.
- Dev на Маке: `brew install tesseract tesseract-lang`; без Tesseract — понятная ошибка «OCR недоступен», загрузка работает.
- Независимые извлекатели полей (см. Decisions) + подсказки для известных банков (K PLUS, BBL); фоновая очередь с прогрессом по SSE; «Распознать заново».
- Тесты — на inline OCR-тексте (с заменёнными именами/хвостами счетов), не на картинках.
- Регрессионный прогон по локальному архиву `samples/slips/` (не коммитится): скрипт показывает долю извлечённых полей и что ухудшилось.

### Этап 3а — Ручная привязка ✅ (сделано 2026-10-27)

Итог: извлекатель времени из имени файла (`time_from_file_name`: K PLUS `0 1 Y DDD HHMMSS …` в обоих форматах, календарные `YYYYMMDD_HHMMSS` / `YYYY-MM-DD at HH.MM.SS`, epoch-мс) — заполняется при загрузке и дозаполняется при старте сервера для старых строк; команды `link_attachment` / `unlink_attachment` / `list_transaction_attachments` / `list_attachment_links` / `list_attachment_candidates(transactionId, windowMinutes)`; блок «Документ» в карточке транзакции с подбором по окну времени; колонка 📎 на экране транзакций; карточка документа вынесена в общий компонент и показывает состояние привязки с кнопкой «Отвязать».
Проверено на реальных данных (2622 слипа + выписка Kasikorn x8136, май—октябрь 2026, 654 списания): время из имени файла есть у всех 2622 документов; у 550 списаний в окне ±5 мин есть хотя бы один кандидат, у 117 — больше одного (обычно слипы других счетов в ту же минуту — их различит автопривязка по сумме).

### Этап 2 + 3б — Распознавание, автопривязка, заметка в колонке ИИ ✅ (сделано 2026-10-27)

Итог (по сценарию пользователя «конец месяца»: загрузить выписки и слипы → выделить месяц → «Действия → Проанализировать документы» → просмотреть заметки в колонке ИИ → категория):
- `ocr.rs`: оттенки серого + увеличение ×1.5 (крейт `image`), Tesseract CLI через stdin (`eng+rus+tha`, в Docker-образе), QR через `rqrr`, разбор тайского slip-verify QR (банк + номер операции). Если сумма не прочиталась — повтор при ×2 (на реальных слипах это вытянуло все такие случаи).
- `slip_extract.rs`: независимые извлекатели по тексту без привязки к вёрстке — дата-время (en-месяцы, 12/24 ч, буддийский год), сумма (рядом с меткой, иначе наибольшая), все суммы (для проверки), направление (подсказка по словам), маска счёта, заметка (после `Memo/Note/Remark/Заметка/บันทึกช่วยจำ`). Кириллические двойники латиницы нормализуются только для структурных полей; заметка читается как есть.
- `document_analysis.rs`: для транзакции — распознать привязанный документ; иначе распознать свободные документы в окне ±5 мин и привязать (`auto`), если ровно один несёт сумму транзакции с совместимым направлением. Статусы: `linked / auto_linked / ambiguous / no_match / no_candidates`.
- UI: массовое действие «Проанализировать документы» (по 2 транзакции параллельно, прогресс, итоги, остановка), заметка 📝 в колонке ИИ, кнопка «Распознать» в карточке документа, быстрые периоды 1/3/6/12 мес.
- Проверено на реальных данных (выписка x8136): июнь — 107 транзакций за 72 с, 79 автопривязок; май — 195 транзакций за 88 с, 128 автопривязок, 3 неоднозначных, 6 без совпадения суммы, 57 без документов рядом.
- Отклонение: заметка в комментарий транзакции **не** копируется — она показывается в колонке ИИ (вопрос о копировании открыт).

### Этап 4 — Категория по заметке (следующий)
- Маленькая кнопка в колонке ИИ: модель предлагает категорию с учётом заметки, пользователь применяет одним кликом или выбирает сам. **Открыт вопрос, куда уходит текст заметки** (облачный провайдер / локальная модель / подсказка по истории категорий).

### Этап 3б — Автопривязка и заметка (исходный план)
- Автопривязка: время (окно ±2–5 мин, с учётом `timezone_offset`) + сумма + направление, кандидат единственный → `auto`; иначе остаётся для ручной привязки. Счёт, если распознан, только сужает выбор.
- Memo → `transactions.comment` (правило — см. открытые вопросы). Ручная привязка/отвязка из «Документов» и из карточки транзакции; карточка показывает слип.

### Этап 4 — Покрытие и пробелы
- По каждому счёту и месяцу: число операций мобильных каналов (K PLUS, MYQR, BBL mBanking) и сколько из них со слипом; месяцы с провалом подсвечиваются (как июль 2026).
- Список «транзакции без слипа» за период.

### Дальше (не в этом плане)
