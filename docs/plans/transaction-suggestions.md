# План: Предложения по транзакциям (категория, перевод между своими счетами, вывод в кэш)

## Goal

Для выбранных транзакций pipeline формирует **предложения** — что с ними сделать — и показывает их в таблице транзакций. Пользователь применяет предложение одним кликом или отклоняет. Ничего не применяется само, существующие категории и связи **никогда не переписываются**.

Три типа предложений:

| Тип | Что предлагается | Чем применяется (уже есть) | Кто формирует |
|---|---|---|---|
| `category` | любой узел текущей иерархии категорий (не обязательно лист) | `set_transaction_categories` (вся сумма в одну категорию) | LLM; позже — история по контрагенту |
| `transfer` | связать с транзакцией на другом своём счёте | `link_transactions` | правила (без LLM) |
| `cash_withdrawal` | вывод в кэш на кассовый счёт | `create_cash_withdrawal` | правила (без LLM) |

Диалог с агентом не нужен: от модели требуется только ответ — категория, уверенность и обоснование уверенности.

## Context

- Сейчас есть диалоговый агент [server/src/ai.rs](../../server/src/ai.rs) (чат по одной транзакции, ответ в `transactions.agent`), массовое «Предложить категории» и блок агента в карточке транзакции. Его недостатки: не видит заметку со слипа, категории передаются плоским списком имён (имя уникально только среди соседей), колонка ИИ убрана — предложения в таблице не видны.
- Заметки: комментарий пользователя (`transactions.comment`) и `memo` из распознанных слипов (`attachments.extraction`), см. [transaction-slips.md](transaction-slips.md).
- По плану слипов **данные слипов в облако не уходят**. Значит, контекст с заметками отправляется только в локальную модель — на DGX Spark (Ollama, OpenAI-совместимый API). Сейчас в настройках ИИ стоит OpenRouter — это нужно будет переключить.
- Данные для правил есть: у Kasikorn в описании маска счёта получателя/отправителя (`Transfer Withdrawal · K PLUS · To X3302 …`, `From X3302 …`), операции банкомата (`Cash Withdrawal · ATM · …`); у счетов — `account_number`, `owner_name`, `kind ∈ {bank, cash}`; у слипа — маска счёта отправителя.

## Рабочий цикл пользователя

Три **отдельных** действия в «Действия ▾», каждое — по выделенным транзакциям, по кнопке, в этом порядке:

1. **«Найти выводы в кэш»** — правила, без LLM.
2. **«Найти переводы между счетами»** — правила, без LLM; только банк ↔ банк.
3. **«Предложить категории»** — LLM; только то, что осталось после 1–2.

Перед ними, как и сейчас, — «Подобрать документы» (появляются заметки со слипов). После каждого действия пользователь просматривает колонку «Предложение» и применяет / отклоняет. Автоматического запуска (после импорта, после подбора слипов) нет. Кнопки «Применить все» на первом этапе нет — сначала посмотреть, как выглядят предложения (ежемесячный разбор — порядка 20 предложений); вернуться к ней после первой большой загрузки.

## Кого пропускаем

| Действие | Пропускается транзакция, если… |
|---|---|
| вывод в кэш | она не списание с банковского счёта, уже в паре (`transaction_links`) или у неё уже есть непросмотренное предложение вывода в кэш |
| перевод | она уже в паре, у неё непросмотренное предложение вывода в кэш или пары (найденной с другой стороны) |
| категория | у неё уже есть категории, она уже в паре **или** у неё непросмотренное предложение вывода в кэш / перевода |

Связанные транзакции (перевод или вывод в кэш) не категоризуются вообще. Если пользователь **отклонил** предложение связи, транзакция снова считается обычной и попадает в категоризацию. Порога уверенности для пропуска нет: пропускает любое непросмотренное предложение связи.

Галочка «пересчитать и те, где предложение уже есть» в окне запуска снимает пропуск по существующим предложениям этого же типа (но не по существующим категориям/связям).

## Архитектура

### Хранение

Новая таблица (миграция):

```sql
transaction_suggestions (
    id              INTEGER PRIMARY KEY,
    transaction_id  INTEGER NOT NULL REFERENCES transactions(id) ON DELETE CASCADE,
    kind            TEXT NOT NULL CHECK (kind IN ('category','transfer','cash_withdrawal')),
    source          TEXT NOT NULL CHECK (source IN ('llm','rule','history')),
    category_id     INTEGER REFERENCES categories(id) ON DELETE CASCADE,   -- category
    partner_txn_id  INTEGER REFERENCES transactions(id) ON DELETE CASCADE, -- transfer
    cash_account_id INTEGER REFERENCES accounts(id) ON DELETE CASCADE,     -- cash_withdrawal
    confidence      INTEGER NOT NULL CHECK (confidence BETWEEN 0 AND 10),
    rationale       TEXT NOT NULL,   -- обоснование уверенности, 1–3 предложения
    reasoning       TEXT,            -- рассуждения модели, если она их вернула
    prompt          TEXT,            -- что именно ушло в модель (для проверки)
    model           TEXT,
    input_hash      TEXT NOT NULL,   -- отпечаток входа: изменился → предложение устарело
    status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending','accepted','dismissed')),
    created_at      TEXT NOT NULL,
    UNIQUE (transaction_id, kind)
)
```

- Одна строка на (транзакция, тип); пересчёт заменяет строку.
- Перевод хранится на **обеих** транзакциях пары; применение с любой стороны закрывает обе.
- `dismissed` запоминается: повторный прогон не предлагает ту же пару / ту же категорию снова, пока не изменился вход (`input_hash`).
- `transaction_categories`, `transaction_links` и кассовые транзакции меняются **только** командой «Применить».

### Действие 1 — вывод в кэш

- Транзакция — списание с банковского счёта, описание похоже на снятие наличных — банкомат или касса в отделении (`Cash Withdrawal`, `ATM`, …; шаблоны — по пресету банка).
- Предлагается **всегда новая** кассовая транзакция (приход на кассовый счёт + связь, команда `create_cash_withdrawal`). Парную запись, внесённую руками, не ищем: момент снятия пользователь в кассу не записывает.
- Кассовый счёт: единственный кассовый счёт в той же валюте; если их несколько — тот, на который чаще всего выводили раньше; если нет ни одного — предложения нет (в итоге действия: «нет кассового счёта в <валюта>»).
- Сумма — сумма списания.

### Действие 2 — перевод между своими счетами

**Окно соседей.** Для каждой выделенной транзакции `X` берутся все транзакции на **других** своих **банковских** счетах (кассовые — забота действия 1) в окне **±5 минут** — до и после `X`, по `occurred_at_utc` — **по всей базе**, а не только среди выделенных (вторая сторона пары может быть не выделена или лежать на счёте, отфильтрованном в таблице). Шире окно не делаем: такие пары редки, их пользователь связывает руками.

Кандидат `Y` годится, если:
- направление противоположное, та же валюта, **равная сумма** (кросс-валютные пока не ищем);
- ни `X`, ни `Y` не в паре, и пара `X–Y` не была отклонена.

Что повышает уверенность:
- маска счёта в описании/контрагенте (`To X3302`, `From X3302`) совпадает с последними цифрами `account_number` счёта `Y` (и наоборот) — сильнейший признак;
- маска счёта со слипа совпадает со счётом `X`/`Y`;
- в контрагенте встречается `owner_name` счёта `Y` (переводы «себе»);
- в описании признак перевода (`Transfer Withdrawal` / `Transfer Deposit`);
- меньше разница во времени.

**Подбор пар — общий, а не жадный по строкам.** Если идти от транзакции к транзакции и брать первого подходящего, при двух одинаковых переводах в одном окне (например, два по 1000 THB с интервалом 3 минуты) пары можно перепутать. Поэтому сначала для всех выделенных собираются все пары-кандидаты с баллами, затем они назначаются по убыванию балла: каждая транзакция попадает максимум в одну пару. Пара записывается на обе стороны, и, дойдя до второй стороны, pipeline её пропускает. Если у транзакции осталось несколько близких по баллу кандидатов, уверенность понижается, а в обоснование пишутся конкуренты.

Обоснование собирается из сработавших признаков: «сумма совпала, разница 2 мин, X3302 = счёт BBL …3302».

### История по контрагенту (этап 3, внутри действия 3)

Нормализованный контрагент / описание → распределение категорий по уже категоризованным транзакциям. Если контрагент встречался ≥ N раз и одна категория набрала ≥ X %, то это предложение `source = history` без LLM (обоснование: «7 из 8 транзакций этого контрагента — «Кафе»»). Иначе распределение передаётся в контекст LLM как подсказка.

### Действие 3 — категория через LLM

**Контекст** собирается в отдельную структуру `SuggestionContext`, в которой **поля баланса нет вовсе** (защита на уровне типа, а не «забыли передать»): дата в местном времени, направление, сумма и валюта, счёт (имя + банк), контрагент, описание банка, комментарий пользователя, заметки со всех привязанных слипов. Плюс тест: построенный промпт не содержит значения баланса.

**Категории** передаются деревом с путями и id, только того вида, что подходит по направлению. Модель может выбрать **любой узел**, а не только лист: если уточнить нельзя, лучше родитель («Еда»), чем угаданный лист.

```
10: Еда — описание
12: Еда / Кафе — описание
13: Еда / Продукты — описание
```

**Ответ** — один JSON-объект без диалога:

```json
{ "categoryId": 12, "confidence": 7, "rationale": "почему уверенность именно такая" }
```

- Сервер проверяет, что id есть в дереве и вид совпадает; иначе предложения нет (записывается ошибка).
- `reasoning` — рассуждения, если модель их вернула (`message.reasoning` / `reasoning_content` / блок `<think>`), сохраняются как есть.
- Перед отправкой проверяем, что endpoint локальный (Spark / localhost / LAN). Если нет — предупреждение в окне запуска, что заметки уйдут в облако.

### UI

- **Колонка «Предложение»** — между «Заметкой» и «Категорией», включается и отключается в «Колонках». В ячейке главное предложение плашкой:
  - категория — цвет и путь категории, уверенность;
  - перевод — 🔗 «Перевод ↔ <счёт>, <время>»;
  - вывод в кэш — 💵 «В кэш → <кассовый счёт>»;
  - устаревшее — приглушено; несколько предложений — счётчик.
- **Клик → модальное окно «Предложения»:** факты транзакции; по каждому предложению — тип, уверенность, **обоснование уверенности**, раскрывающиеся **рассуждения модели** (если были) и «что ушло в модель» (видно, что баланса там нет); кнопки «Применить», «Отклонить», «Пересчитать». Для перевода — карточка второй транзакции.
- **Три массовых действия** в «Действиях»: «Найти выводы в кэш», «Найти переводы между счетами», «Предложить категории» (последнее заменяет нынешнее). У каждого — прогресс, итог (найдено / пропущено с причинами) и галочка «пересчитать и те, где предложение уже есть».
- Старый диалоговый агент удаляется: блок агента в карточке транзакции, `AgentSection` / `AgentYaml` / `agent-run.ts`, команды `ai_transaction_chat` / `set_transaction_agent`, колонка `transactions.agent` (на стенде пустая). Настройки провайдера ИИ и «Проверить соединение» остаются.

### Эталонная выгрузка (для оценки моделей и правил)

Пользователь выделяет транзакции, которые размечены правильно, → «Действия ▾ → Выгрузить эталон» → браузер скачивает один JSON-файл. Пользователь присылает его Cody (кладётся в `.tmp/`, в репозиторий не попадает — там реальные контрагенты и заметки).

Состав файла:
- `meta` — версия формата, дата выгрузки, версия приложения;
- `categories` — всё дерево (id, путь, вид, описание);
- `accounts` — id, имя, банк, вид, валюта, последние 4 цифры номера, имя владельца;
- `transactions` — для каждой выделенной:
  - **ровно тот `SuggestionContext`, который ушёл бы в модель** (без баланса);
  - эталон: категории с долями (id + путь), партнёр по паре (id), признак вывода в кэш;
- `neighbors` — все транзакции на других счетах в окне ±5 мин от выделенных (тот же контекст, без баланса): без них правила перевода оффлайн не проверить.

На этом файле скрипт оценки (`.tmp/`, не коммитится) прогоняет модели и правила: точное попадание в категорию, попадание в верхний уровень, калибровка уверенности, время на транзакцию; для пар — найдено / пропущено / ложные.

## Решения (2026-10-28)

- Три отдельных действия по кнопке: «Найти выводы в кэш» → «Найти переводы между счетами» → «Предложить категории».
- Вывод в кэш — всегда новая кассовая транзакция, парную ручную запись не ищем.
- Переводы — только банк ↔ банк, одна валюта, окно ±5 минут; всё, что дальше, пользователь связывает руками.
- Категория — любой узел дерева, не только лист.
- Не категоризуются: уже категоризованные, уже связанные, с непросмотренным предложением связи.
- Категория у транзакции не мешает предложить для неё связь.
- Кнопки «Применить все» на первом этапе нет.
- Данные для оценки — эталонная выгрузка из приложения (присылается позже).
- Номер миграции — 021+ (020 занят параллельной работой по слипам).

### Решение по агенту категорий (2026-10-28, после первой эталонной выгрузки)

- **Агент учится на том, что размечает сам пользователь, во время работы приложения.** У каждого пользователя свои категории и своя манера разметки, поэтому ни модель, ни промпт не «зашиваются» под конкретный набор данных. В каждый запрос к модели подставляются примеры из **его же** размеченных транзакций:
  - тот же контрагент — какие категории ему ставились (распределение + несколько последних примеров);
  - похожие описание банка / заметки со слипов / комментарий;
  - тот же контекст жизни — какие категории пользователь ставил в этот период (в первой выгрузке 38 из 108 размеченных — «Путешествия как подарок родителей», это решает контекст, а не контрагент).
- Примеры — только решения пользователя: категории, поставленные вручную, и принятые предложения. Отклонённые предложения в примеры не идут.
- Эталонная выгрузка — **только тест**, а не обучающие данные. Оценка честная: для каждой эталонной транзакции примеры берутся только из разметки, сделанной до неё по времени, и сама она в примеры не попадает.

## Принять предложения массово (2026-10-29)

«Действия ▾ → Автоматически → Принять предложения…»: для выделенных транзакций окно с разбивкой ожидающих предложений по уверенности (10…0) и видам (категории / переводы / кэш), колонка «Не ниже» — сколько будет принято при пороге. Пользователь выбирает порог и виды; предложения применяются по одному, как кнопкой «Применить» (перевод — один раз на пару; метки «агент не уверен» не применяются), с прогрессом и «Остановить». Связи, созданные так, получают категории «<<--->>» (см. [transfer-categories.md](transfer-categories.md)).

## Прогнать отклонённые ещё раз (2026-10-29)

Отклонённое предложение по умолчанию не предлагается снова, пока не изменится то, из чего оно посчитано (`input_hash`). В окнах «Найти выводы в кэш», «Найти переводы между счетами» и «Предложить категории» есть галочка «Прогнать и отклонённые ранее (N)» — видна, когда среди выделенных есть отклонённые предложения этого вида (`dismissed_suggestion_counts`). С ней отклонённые считаются заново (`include_dismissed`); «Пересчитать / Спросить заново» по-прежнему отвечает только за уже существующие и неуверенные. Агент с этой галочкой спрашивает модель заново и там, где отклонённой была метка «агент не уверен».
